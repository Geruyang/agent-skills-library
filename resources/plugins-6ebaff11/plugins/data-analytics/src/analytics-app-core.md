# Analytics App Core

Use this shared foundation for generated Data Analytics dashboard and report artifacts. Public skills should keep separate intent contracts, but reuse this core for bounded snapshots, source safety, app runtime behavior, and validation helpers.

Use this file after selecting a supported delivery surface: an MCP Apps chart/table widget, a Data Analytics MCP report/dashboard artifact, or a self-contained HTML report/dashboard built from the canonical artifact contract. Discover the current host's actual tools, rendering contract, permissions, and connected services before selecting a surface. Root skills remain delivery-mode neutral: if the user asks for chat, notebook, BI, Streamlit, slides, or no rendered artifact, do not apply MCP widget/app mechanics except for the general safety principles. Portable HTML uses the shared manifest, snapshot, source, and validation contract plus the packaging workflow below; it does not use MCP UI calls. If a host explicitly identifies a mode where MCP UI delivery is unsupported, select another available surface rather than treating visible tool names as proof of rendering support. Hosted Sites publication is available only through a discovered supported lifecycle and the user's authorization; otherwise use self-contained HTML when that meets the request.

## Shared Contract

- When the Data Analytics `render_artifact` tool and its native reader are actually supported by the current host, use that documented handoff for bounded dashboard/report manifests. For example, a compatible ChatGPT Desktop session may provide this surface; its availability does not extend automatically to TRAE, Claude, or another host. Otherwise use an equivalent discovered renderer or the portable HTML workflow below. Offer hosted sharing only when relevant and publish only after the user explicitly requests or accepts it; existing explicit authorization need not be requested again.
- Keep generated artifacts snapshot-first.
- Store source-backed data in `snapshot.datasets` and keep rows bounded and aggregate unless a detail table is explicitly needed.
- Use the canonical snapshot shape: `snapshot.datasets` is an object keyed by dataset id, and each value is a plain array of reviewed row objects. Keep column metadata in the manifest, not inside `snapshot.datasets`.
- Declare source artifacts in the manifest when the reader needs provenance,
  query text, or citation metadata.
- Native chart specs are defined by MCP tool descriptions and enforced by artifact validation. Shared guidance should not duplicate field-level chart schema.
- Give each native artifact table an explicit `defaultSort` chosen to make the initial view answer the table's question. Sort ranked magnitudes or movements descending, chronological sequences in the reading direction that best supports the analysis, and use a field declared in `columns`.
- Use `ready`, `partial`, `blocked`, and `fixture` snapshot statuses across dashboard and report artifacts.
- Reports must expose a visible in-report title. Set `manifest.title` to the reader-facing title, and make the first report markdown block a matching `#` heading.
- Give every independently laid out or editable major report section its own markdown block. Do not put multiple peer `##` section headings in one markdown body; use `###` headings only for subordinate content that should remain in the same card.
- Treat `partial` and `blocked` as first-class states with visible access notices, not buried caveats.
- Reserve snapshot-level access issues for missing required data in `partial`
  or `blocked` artifacts. Optional source limitations in an otherwise `ready`
  artifact belong in caveat sections, source metadata, or report notes.
- Every native chart block must expose the actual SQL or source path used to generate its chart dataset through the current MCP artifact schema.
- Native chart source datasets should remain useful beyond visible encodings when safe reviewed context is available. Preserve candidate grouping fields, numerators, denominators, ranks, baselines, comparison periods, and adjacent measures for auditability and realistic chart switching.
- Use the same canonical `source` structure for inline charts, inline tables, artifact metric cards, artifact charts, artifact tables, and `manifest.sources[]`: put runnable SQL/code in `source.query.sql`, put the human-readable query summary in `source.query.description`, and put durable query metadata in `source.query.engine`, `source.query.id`, `source.query.url`, `source.query.executed_at`, and `source.query.language`.
- Source metadata must be specific enough to validate: use actual table identifiers such as `example.analytics.fact_revenue`, not query nicknames or semantic labels, and put those identifiers in `source.query.tables_used` when they cannot be inferred from SQL.
- Declare static source predicates in `source.query.filters`, including date windows, cohort/population rules, material exclusions, and sampling/limit rules. Use artifact `manifest.filters` only for interactive viewer controls.
- Metric definitions must describe calculations, not only source columns. For ARR, include the aggregation/window, currency/unit, date grain, and material exclusions such as internal orgs, test traffic, true-up rows, or other accounting adjustments.
- KPI and metric cards must use accurate display semantics and scale. Set `format` to the value type being rendered, such as `percent` only for rates/shares and `currency` only for money. Percent format always expects fractional-rate values: pass `0.98` for `98%`, `1` for `100%`, and `2` for `200%`. If the reviewed data is already in percentage points such as `98`, use `format: "number"` with `unit: "%"`, and make that scale clear in the metric label or definition. Prefer passing unscaled numeric values and using compact formatting so the artifact renders `K`, `M`, or similar scale suffixes accurately. When a query intentionally pre-scales a value, make that scale visible in the metric label, such as `B tokens` or `revenue, $M`; do not rely on SQL aliases, field names, or query comments to imply it. Do not use a percent or currency format just because the metric is a change; format the actual value's unit and label the comparison separately.
- Reader-facing numbers in cards, chart labels, axes, tooltips, headings, and narrative text should use compact shorthand for large values, such as `1.2k` instead of `1,201`, unless the surface is an exact lookup table or audit detail where precise values are the point.
- KPI and metric cards must be interpretable without reading the SQL. If a metric label depends on business logic rather than a plain count or sum, define the metric in reader-facing terms and preserve the exact calculation in `source.query.metric_definitions`. Every card used by a dashboard or report `metric-strip` must declare `sourceId` or inline `source` provenance so its top-right data-source action can open the shared source modal with the exact query, tables, filters, metric definitions, snapshot, and reviewed data rows for that card.
- A markdown block may use `sourceId` as block-wide provenance only when all quantitative claims in its body come from that one canonical source. Split mixed-provenance claims into separate blocks, omit `sourceId` on title-only or prose-only blocks, and never guess a source. The referenced source may be structured query output, a file, or a document and does not need `source.query.sql`.
- Metric-strip cardinality is decision-driven, not layout-driven. Do not pad or cap a strip at four cards. Include every distinct headline metric needed for the decision and omit redundant or vanity cards; the shared dashboard/report renderer chooses a balanced responsive column count for any number of cards.
- Give each metric card exactly one headline metric. One headline does not mean one `metrics[]` entry. Later entries add short, directly comparable context for that headline, such as its prior-period value, target, or delta. Preserve a decision-relevant directional comparison as a later metric when it is already used in the executive summary or findings; move independent secondary measures to their own cards, charts, tables, or narrative. Keep the card description specific to the headline metric and its comparison context.
- Definitions should clarify the population being measured, the event or state being counted, the time window, the aggregation method, and any important thresholds, exclusions, numerator/denominator logic, or source-specific meaning. This is especially important for rates, averages, shares, lifecycle or stage metrics, eligibility or activity metrics, quality outcomes, and version/source-attribution metrics.

## Inline Widgets

- Inline widgets are for compact, reviewed intermediate or final values in non-report runs. Do not render inline chart or table widgets during report-mode work; report charts, tables, and previews belong in the selected report surface.
- If the current host exposes a compatible Data Analytics widget surface, use its documented `render_chart` operation for compact non-report visuals and `render_table` for reviewed row previews or exact lookup tables. Otherwise discover an equivalent MCP/API renderer or create an appropriate self-contained HTML/static visual with a verified local tool. Do not call these names on an unrelated service or assume that a host mode supports UI rendering merely because tools are listed.
- `charts_widget_v2`, `genui`, and `app_block` are host-specific rendering contracts. Use one only when current host documentation explicitly exposes it and confirms the payload schema. For a supported ChatGPT `charts_widget_v2` surface, its documented `bar`, `line`, `pie`, and `scatter` branch may apply; do not emit proprietary content tokens or bare widget JSON in TRAE, Claude, or another host that cannot render them. A fallback does not require a deliberately unsupported rendering attempt.
- Honor explicit Python, static image/file, notebook, and export requests. When no suitable native renderer exists, use a supported HTML or static chart path, or a compact table if no visual can be delivered. Verify the returned or saved result through an available preview/inspection capability. Do not treat `ok:true` as proof that a visual rendered; report missing rendering or inspection capabilities as a specific limitation.
- Chart and table widget payloads are query-shaped and pass the same canonical `source` object. The source query must contain the durable original SQL used to materially produce the reviewed rows, plus any durable query ID or URL as metadata. If a later query only reshapes, sorts, limits, or reselects from already computed rows for widget rendering, keep that later query out of `source.query.sql`; record it as transformation context instead of replacing the original provenance.
- Treat `source.query.sql` as provenance for the widget's source experience, not as visible answer content. Do not duplicate that SQL in the surrounding final chat response or chart narrative unless the user explicitly asks to see, write, review, debug, or receive SQL or query methodology.
- The source query text must be runnable SQL in the named engine. Do not pass prose such as "Revenue bridge SQL executed in Databricks..." as `source.query.sql`; put that prose in `source.query.description`.
- Default the chart title to a neutral, descriptive label that identifies what is plotted, such as the metric, comparison, dimension, or time scope. Do not infer a narrative takeaway, claim, clever headline, or new jargon for the title unless the user explicitly requests a takeaway-led title.
- The chart subtitle should add a reader-facing insight not already covered by the title. Put source names, query IDs, table names, SQL intent, metric definitions, and provenance in source metadata or notes instead.
- Make widget tables exploration-ready with useful dimensions, measures, time columns, candidate grouping fields, ranks, benchmarks, comparison-period values, or adjacent measures from reviewed results. Customer, account, company, segment, and product names are valid analytical dimensions when they are relevant. For scatter widgets, prefer one row per meaningful observation rather than a handful of broad aggregates; retain a stable point label, numeric x and y measures at the same grain, denominator or sample-size fields, one volume/size candidate, and one interpretable grouping or filter field when safe. Retaining a field for exploration does not mean the shipped chart should bind it as color, series, or grouping.
- Use tidy long-form rows when that keeps chart switching understandable.

## MCP Safety And Rendering

- If the user explicitly waives MCP widgets or app rendering, continue through the selected non-MCP surface and preserve SQL, source notes, and visual QA in that surface's normal supporting artifacts.
- Do not send hidden reasoning, credentials, secrets, direct personal contact/payment identifiers, or unvalidated calculations into widget or artifact payloads. Reviewed customer, account, or company names may be included when they are needed for the analysis.
- Keep exposed rows compact, reviewed, and at a clear analytical grain. Use deterministic samples for larger results, set the full reviewed row count, and mark truncation when applicable.
- After running a durable source query, expose the first 10 reviewed rows, or a deterministic 10-row sample when the query result is too large or naturally unordered, so the user can validate the grain and columns behind the chart/table.
- Preserve the actual SQL, source file path, or reproducible transformation that materially produced exposed rows. Do not replace query text with a prose source description, metric definition, filter summary, or query ID list.
- For the Data Analytics MCP branch, discover and call its actual `validate_artifact` operation before the first supported `render_artifact` handoff. A different MCP/API branch must use its own documented validation contract. Iterate on validation errors before visible rendering. If validation is unavailable, report that native branch as blocked; the packaged local validator can still support portable HTML when its dependencies are present.
- Call the supported native handoff only after validation succeeds and the current host confirms reader support. If rendering fails, record the blocker and choose another supported delivery path instead of repeated visible retries. A host mode that cannot display MCP artifacts should use the HTML workflow or a user-authorized hosted route; it does not authorize publication by itself.
- If an inline chart/table widget fails after one targeted retry, continue the analysis through another appropriate surface and note the omission reason.

## Portable HTML Packaging

Use this path whenever the build-report or build-dashboard workflow selects HTML, regardless of the current host's skill invocation syntax. The HTML artifact is a read-only packaging of the same canonical Data Analytics artifact used by the MCP app, not a separately authored report implementation. Discover an authorized Node runtime and the installed script/resource locations first. The package needs the delivery scripts, local validator, plugin metadata, icon files, and compressed portable-reader assets; do not assume an original plugin cache layout. If this implementation's required resources are unavailable, report that packaging dependency as blocked. An equivalent HTML implementation may be used only when it preserves the canonical payload, provenance, safety, and verification requirements; do not silently label a simpler substitute as the packaged reader.

1. Save `artifact.json` in the exact top-level shape accepted by `validate_artifact`: `surface`, `manifest`, `snapshot`, `sources`, and optional `package_info`. Follow the shared contract above. Reports use `surface: "report"`; dashboards use `surface: "dashboard"`. Keep the complete ordered `manifest.blocks`, native cards/charts/tables, bounded `snapshot.datasets`, access issues, and canonical sources in this file.
2. Give every source-backed card, chart, and table an inline `source` or a `sourceId` that resolves to `manifest.sources[]`. Apply the shared block-wide `sourceId` rule to markdown blocks with quantitative claims so the portable reader can expose those values' provenance too. Preserve exact source-system, table/view/dataset/file/document identity and the canonical query metadata needed for trust. The portable reader and its builder-generated source affordances, tooltips, detail views, and semantic source inventory derive from this metadata; do not invent provenance. Packaging preserves safe canonical source objects exactly rather than sanitizing them. Credentials, credential-bearing URLs, and machine-local or parent-traversing paths are rejected with their artifact path; they are never silently removed or rewritten.
3. Resolve `deliver_portable_artifact.mjs` from the installed skill or plugin metadata, verify its resource-root configuration, then build and verify the final file with the selected Node runtime. Use the active shell's quoting rules; this is a Bash example:

   ```bash
   node "<verified path to deliver_portable_artifact.mjs>" \
     --input artifact.json \
     --output report.html
   ```

   The delivery command calls the local canonical `validate_artifact` implementation and writes a temporary packaged reader. When a compatible installed Chromium is available, it extracts shared-renderer chart SVGs and runs the bounded browser verifier against the same artifact before writing the final local file. Without one, it writes the file only after exact payload equality and the required runtime, reader, and semantic-fallback roots pass structural verification. This local packaging command is not authorization for external hosting. Fix reported validation, safety, source, payload-size, or browser errors in `artifact.json`, then rerun the same command.
4. Treat `report.html` as generated output. The builder embeds the read-only portable artifact reader, shared app styling/tokens, layout, native charts and tables, and supported reader interactions. It disables MCP-host-only, editing, persistence, refresh, export, and sharing controls. Its replacement `package_info` is the portable delivery envelope, not provenance sanitization.
5. The builder also emits a semantic HTML fallback in manifest block order, including readable narrative, metric cards, chart-data summaries, tables, access notices, and source provenance. This fallback is the no-script, unsupported-browser, print, and conversion safety path; it is produced from the same validated artifact data. On browsers that lack the APIs required by the enhanced reader, the fallback remains readable but is not fully interactive.
6. Keep the output self-contained. It must not require a CDN, remote script, network fetch, MCP host API, local server, runtime sidecar, chart-image sidecar, or sibling data file.
7. Treat a compact success receipt with `stages.verification: "passed"` as sufficient per-report QA. It proves exact equality between the canonical source artifact and the payload embedded in the HTML, then runs a strict enhanced-reader smoke using an already installed Chromium: desktop plus narrow layout, expected rendered counts, nonzero geometry, overflow, a representative source menu/dialog flow, and no external requests or browser errors. It never installs a browser and writes a screenshot only on failure. If the receipt instead says `stages.verification: "structural_only"`, no compatible browser was available: exact payload equality and the required runtime, reader, and semantic-fallback roots passed, but chart SVG extraction and per-artifact browser QA did not run. Retain the delivered semantic chart tables and disclose that QA limitation. Do not add bespoke browser automation or repeat visual inspection. Multi-engine, keyboard, touch, print, semantic-fallback, conversion, and pixel-parity certification belongs to shared reader CI when the runtime or builder changes. Use the generated HTML directly for PDF, Google Docs, or Google Slides conversion.

Do not create portable HTML in parallel with an MCP artifact in the same run unless the user explicitly requests a separate second delivery mode.

## Hosted Sites Artifact Publishing

- Discover whether the current host has the complete Sites publication lifecycle or an equivalent authorized hosting service. Use it only after the user explicitly requests publication or accepts a sharing offer; no host mode, tool availability, or request for a durable local report grants publication authority by itself. Continue within an existing explicit authorization without asking again. If hosting is unavailable, declined, or fails, offer the verified self-contained HTML and report the hosted-delivery blocker accurately.
- Keep the requested primary delivery surface. A compatible native artifact can remain primary in ChatGPT Desktop or another supported host; HTML can remain primary elsewhere. Do not add a second hosted copy solely because a publishing tool becomes available.
- For the actual Data Analytics-to-Sites branch, use the documented `export_artifact_package` operation after validation. Discover a supported Sites worker-starter checkout or project workflow first, then pass a verified writable checkout path as `output_dir` so `worker/index.js` and hosting metadata are retained. Do not rely on a server's OS-temp path across tools. Other hosting services must use their own verified package/deployment contracts; report missing required lifecycle operations instead of inventing equivalents.
- The exported package must preserve the canonical `datascience-artifact-widget.html` runtime and its shared chart detail widget. It should bootstrap the hosted page with the validated payload while also serving `/api/manifest`, `/api/snapshot`, `/api/package`, `/api/presentation`, `/api/source-file`, and `/api/inline-chart-widget` for the runtime, plus `db/schema.ts` when presentation editing is enabled.
- Do not rebuild the report as standalone HTML, inline CSS charts, or a separate one-off viewer. Hosted sharing is a packaging step for the current artifact, not a second rendering implementation.
- Treat Sites exports as reader surfaces by default. When the actual Sites presentation-editing experiment is available, it may seed one editor from a verified owner-only Sites access policy or an explicitly confirmed personal-site owner; that user may save title, text, component layout/order, and deleted-block overrides in the Site database. Do not expose a restore-deleted-blocks action. Creator-only refresh and HTML/PDF/Google Doc/Slides actions must return to an authenticated, authorized authoring workflow instead of letting the public Site access connectors. In a ChatGPT-integrated deployment, use verified current ChatGPT Desktop/Work Mode handoff links only when that integration is supported; other hosts must use their own documented handoff or omit the unavailable action. Never fabricate a deep link or start another chat implicitly. Keep republishing from inside the Site, Site/project deletion, raw HTML editing, chart-definition changes, and table resizing disabled. Underlying artifact or data changes still require a new saved Sites version, with stable-ID presentation overrides preserved.
- Keep static HTML and PDF exports content-only: include the report or dashboard title, narrative, charts, tables, and source details, but omit the interactive top bar and app-only controls.
- State that published Sites data is a snapshot rather than a live connector.

## Encoding Rules

- Bind color, series, grouped, or stacked behavior only when there is a meaningful second categorical dimension beyond the x/y category, such as segment, product line, period plus component, or observed series.
- Treat `by <dimension>` in a chart title, subtitle, or visible header as an encoding contract. An x/y axis dimension already satisfies that contract. If `<dimension>` is not on an axis and is not otherwise visibly encoded through color/series, grouped or stacked marks, faceting, or direct labels, remove `by <dimension>` from the visible text. For `render_chart`, a time or category x-axis chart titled `... by segment` or `... by market` must bind that second dimension through `chart.fields.color.field` or an equivalent visible grouping rather than only retaining it in the source table.
- When a grouped chart uses color, series, grouped, stacked, or faceted behavior, make the group names visible with a legend or direct labels. A chart does not satisfy a `by <dimension>` title if the reader cannot identify the rendered groups from the chart itself.
- Do not bind color, series, grouped, or stacked behavior to the same category already used for x or y just to color bars. A bar chart whose x-axis is `modality` and y-axis is `delta` should not also color by `modality`; use palette styling, direct labels, or a single mark color instead.
- Hide legends for single-series charts. Prefer direct labels when the axis or table labels already name the categories.

## Surface Split

- Dashboard skills own monitoring and exploration: KPI hierarchy, chart-first canvas, dashboard-wide filters, neutral markdown cell headers, and operational QA.
- Report skills own answer-first synthesis: audience, findings,
  insight-led markdown cell headers, markdown narrative cells, section evidence, recommendations, citations, caveats, export, and reproducibility.
- Shared code owns mechanics: manifest normalization, JSON IO, markdown page/cell header rendering, source safety, sensitive payload checks, and reusable validation primitives.
- Shared chart support lives in `analytics-app/scripts/chart_contract.py`. Dashboard and report validators should import the same supported type list, palette roots,
  series-shape checks, mixed-metric checks, and mixed-scale checks so newly added or removed native chart types do not drift between surfaces.
- Shared chart presentation support lives in `analytics-app/charting/chart-contract.ts`, `analytics-app/charting/chart-capabilities.ts`, and `analytics-app/scripts/chart_contract.py`. Keep palette kind, legend behavior, value label,
  and reference-line options declared in the manifest and validated in both dashboard and report artifacts before adding one-off renderer behavior.
- Shared design support lives in `analytics-app/scripts/design_contract.py`. Validators should require a structured `DESIGN.md` without freezing users out of artifact-level customization.

## Report Mode Boundary

MCP app reports and HTML reports are separate delivery modes. Use `render_artifact` only for a discovered compatible Data Analytics reader handoff; do not also generate `report.html` unless the user requests a second output. If native handoff is unsupported in the current host or mode, select self-contained HTML or an explicitly authorized hosted route. For PDF, Google Docs, or Google Slides conversion, choose HTML report mode in the build-report workflow, author the canonical `artifact.json`, and use the portable builder above. Discover the required renderer or authenticated document-conversion service before promising the final format; if missing, keep the verified HTML and report that conversion as blocked. The builder packages the shared app reader and semantic fallback into one self-contained file; do not create a second chart runtime or sidecar chart files.
